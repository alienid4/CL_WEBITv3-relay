你要協助的專案是一套 IT 資產盤點系統（後端 FastAPI + SQLite，前端 Nuxt 3）。
**先讀根目錄的 `AGENTS.md`，那是硬規則，不是建議。** 讀完再往下做。

## 你的角色

**你只寫測試。程式碼不歸你改。**

- 可以動：`APP/asset-module/frontend/tests/**`、`tests/asset_module/**`
- 不可以動：其他任何檔案（含 `APP/` 底下的原始碼、設定檔、schema）

發現程式有 bug 時：**寫一條會紅的測試，並在交接文件裡說明。不要自己去改程式。**
那條紅測試就是最好的 bug 報告——它可以被重現，而文字描述不行。

## ⚠️ 你的產出會 email 出公司，不得有真實資料

這是法遵要求。**禁止**出現真實 IP、真實主機名、公司名、人名、分機、資產序號。
一律改用 `10.99.x.x`、`SECSVR001-001`、`host-a`、`tester`。

你拿到的程式碼**已經去識別化過**，裡面的 IP 與名稱本來就是假的，照抄那些就對了。
如果看到疑似真實的東西，**回報但不要複製**。

## 第一批任務

替下面五個目標補前端測試。**這五個刻意挑過：它們完全不依賴 Nuxt 的自動匯入，
所以可以直接掛載測試，不需要 mock 任何 Nuxt 內部。**

1. `composables/useToast.ts`
2. `components/SortTh.vue`
3. `components/DataCell.vue`
4. `components/DonutChart.vue`
5. `components/SearchableSelect.vue`

**先看 `APP/asset-module/frontend/tests/useSort.spec.ts`**——那是樣板，
照它的形狀寫（測試名稱講「守什麼」、每個 assert 註明為什麼重要、測錯誤路徑）。

跑測試：
```
cd APP/asset-module/frontend
npm test
```

## 這個專案最在意的四件事（測試要往這裡打）

1. **「查不到」跟「沒有」是兩件事。** 畫面上要分得出來。
   顯示 `0` 跟顯示「沒有資料」不能混，混了人會拿假的 0 去做決定。
2. **邊界**：0 筆、1 筆、空字串、null、全部同一類。
3. **兩個方向都要釘。** 條件寫反了，只釘一邊的測試照樣會過。
4. **冪等**：同樣的操作做兩次，結果要一樣。

## ⚠️ 沒看過它紅過的測試，不算測試

寫完每一條，自問：**「程式壞成什麼樣，這條會紅？」**
答不出來的那條是裝飾品——比沒有更糟，因為它給人「這裡有防護」的錯覺。

跑得動測試就實際做一次：把對應的程式改壞、確認那條真的會紅、再改回來
（改回來，**不要把改壞的版本交出去**）。跑不動就把「我預期它在什麼情況下會紅」
寫進交接文件。

## 你怎麼交件

產出一份 Markdown，格式**完全照** `AI/CODEX_HANDOFF_TEMPLATE.md`，不要自由發揮。

三條硬規則：

1. **一節一個檔案，給完整路徑與完整內容。**
   不准用 `...`、「（其餘不變）」、diff 片段。對方要能機械式還原成檔案。
2. **報事實，不下結論。** 「哪條測試、完整輸出、怎麼重現」是事實；
   「我認為是 X 造成的」是推論——可以寫，但必須標明是推論。
   你看不到全貌，一個標成事實的錯誤推論會害人往錯方向查。
3. **每條測試標「預期：綠」或「預期：不確定」。**
   對方一律當未驗證，有這個標籤才分得出「你發現了 bug」跟「你把測試寫壞了」。

交接文件的最後兩節是**「我不確定的」**與**「沒做完的」**——**寫滿它們**。
留白會被當成「已驗證」直接接手，那個錯誤會被帶到下一輪，而且愈晚發現愈貴。

現在開始：先讀 `AGENTS.md` 與 `tests/useSort.spec.ts`，然後告訴我你打算怎麼下手，
**先不要動手寫**。
